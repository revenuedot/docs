# What does Play Billing BILLING_UNAVAILABLE (3) mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/play-billing-billing-unavailable.md
Description: BILLING_UNAVAILABLE (3) means Google Play cannot bill this user: an old Play Store, an unsupported country, a blocked account or a declined payment method.

Play Billing BILLING_UNAVAILABLE (3) means a billing problem on the user's side stopped the purchase.

## Quick facts

| | |
|---|---|
| Error | `BillingClient.BillingResponseCode.BILLING_UNAVAILABLE` (3) |
| Where | Google Play Billing Library (`BillingResult.responseCode`) |
| What the vendor says | A user billing error occurred during processing. |

## Cause

- Google lists these examples: the Play Store app on the device is out of date, the user is in an unsupported country, an enterprise administrator has turned purchases off, or Google Play cannot charge the user's payment method (for example an expired card).
- Google also names a Play Store that the system blocks, for instance in an OEM kids mode, where the `BillingResult` debug message says the Play Store is blocked.
- These are conditions on the device or the account, so an automatic retry does not fix them.

## Fix

1. Do not retry automatically. A manual retry works only after the user fixes the condition, for example by updating the Play Store.
2. Show a short message and a **Try again** button; Google notes the user probably saw the reason in the Play purchase screen.
3. Read `debugMessage` and log it, because it can name the cause, such as a blocked Play Store.
4. Do not unlock content.

## Example

```kotlin
import com.android.billingclient.api.BillingClient
import com.android.billingclient.api.BillingResult

// No automatic retry: tell the person, and let them try again after they fix the account or update the Play Store.
fun onPurchaseResult(result: BillingResult, showMessage: (String) -> Unit) {
    if (result.responseCode == BillingClient.BillingResponseCode.BILLING_UNAVAILABLE) {
        println("BILLING_UNAVAILABLE: ${result.debugMessage}")
        showMessage("Google Play cannot complete purchases right now. Check the Play Store and your payment method, then try again.")
    }
}
```

# What does Play Billing DEVELOPER_ERROR (5) mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/play-billing-developer-error.md
Description: DEVELOPER_ERROR (5) means the app used the Play Billing API wrongly: bad arguments, an unsigned app or missing permissions. Read the debug message and fix the call.

Play Billing DEVELOPER_ERROR (5) means the app called the Play Billing API incorrectly.

## Quick facts

| | |
|---|---|
| Error | `BillingClient.BillingResponseCode.DEVELOPER_ERROR` (5) |
| Where | Google Play Billing Library (`BillingResult.responseCode`) |
| What the vendor says | The error comes from incorrect use of the API. |

## Cause

- Google's examples: invalid arguments such as an empty product list where one is required, or a misconfigured app, such as one that is not signed or lacks the permissions it needs in its manifest.
- Google also says that wrong parameters passed to `launchBillingFlow` can cause it, and that the debug message gives more detail.
- It is a fatal error for that call, so a retry with the same arguments fails again.

## Fix

1. Read `billingResult.debugMessage` and log it first; it usually names the problem.
2. Check the arguments of the failing call: a non-empty product list, product details from the same `BillingClient`, valid billing flow params.
3. Install a signed build: Google names an app that is not signed as one cause.
4. Check that the manifest has the permissions Google's integration guide requires, then rebuild.

## Example

```kotlin
import com.android.billingclient.api.BillingClient
import com.android.billingclient.api.BillingResult

// DEVELOPER_ERROR is a bug in how the app calls the API: the debug message is the fastest clue.
fun onBillingResult(result: BillingResult) {
    if (result.responseCode == BillingClient.BillingResponseCode.DEVELOPER_ERROR) {
        println("DEVELOPER_ERROR: ${result.debugMessage}")
    }
}
```

# What does Play Billing ERROR (6) mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/play-billing-error.md
Description: ERROR (6) means Google Play failed internally during a billing call. It can be transient: retry with exponential backoff, and contact Google Play if it persists.

Play Billing ERROR (6) means a fatal error inside Google Play during the billing call.

## Quick facts

| | |
|---|---|
| Error | `BillingClient.BillingResponseCode.ERROR` (6) |
| Where | Google Play Billing Library (`BillingResult.responseCode`) |
| What the vendor says | A fatal error occurred during the API action. |

## Cause

- Google describes it as an internal Google Play error that may be transient or caused by an unexpected condition during processing.
- The code does not say which call or condition failed, so the debug message and your own logs are the only detail.
- It is not caused by your arguments (that is `DEVELOPER_ERROR`) or by the network (that is `NETWORK_ERROR`).

## Fix

1. Retry with exponential backoff for background work; use a simple retry when the person is waiting.
2. Mind how long you retry during a user interaction, as Google advises.
3. Log the response code, debug message and Play Store version so you can report a persistent case.
4. Contact Google Play support if the error keeps coming back.

## Example

```kotlin
import com.android.billingclient.api.BillingClient
import com.android.billingclient.api.BillingResult
import kotlinx.coroutines.delay

// Google: ERROR may be transient, so back off and retry a few times, then give up and report it.
suspend fun acknowledgeWithRetry(acknowledge: suspend () -> BillingResult): BillingResult {
    var wait = 2_000L
    var result = acknowledge()
    repeat(2) {
        if (result.responseCode != BillingClient.BillingResponseCode.ERROR) return result
        delay(wait)
        wait *= 2
        result = acknowledge()
    }
    return result
}
```

# What does Play Billing FEATURE_NOT_SUPPORTED (-2) mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/play-billing-feature-not-supported.md
Description: FEATURE_NOT_SUPPORTED (-2) means the Play Store on the device does not support the Billing feature you called. It cannot be retried; check isFeatureSupported() first.

Play Billing FEATURE_NOT_SUPPORTED (-2) means the Google Play Billing feature you called is not supported on this device.

## Quick facts

| | |
|---|---|
| Error | `BillingClient.BillingResponseCode.FEATURE_NOT_SUPPORTED` (-2) |
| Where | Google Play Billing Library (`BillingResult.responseCode`) |
| What the vendor says | The requested feature is not supported by the Play Store on the current device. |

## Cause

- Google says the cause is likely an old Play Store version on the user's device. Its example is a device that does not support in-app messaging.
- Google lists it among the non-retriable responses: trying again on the same device gives the same answer.
- It is a property of the device and Play Store version, not of your app's configuration.

## Fix

1. Call `billingClient.isFeatureSupported(FeatureType)` before you use an optional feature, and only use the feature when the response is `OK`.
2. Do not retry the call. Hide the feature or use a fallback for that device.
3. Do not show a purchase error to the person: the product itself may still be sellable without the optional feature.
4. Keep the Billing Library current, because newer versions know more feature types.

## Example

```kotlin
import com.android.billingclient.api.BillingClient

// Ask before you use an optional feature. FEATURE_NOT_SUPPORTED cannot be fixed by retrying.
fun supportsInAppMessaging(billingClient: BillingClient): Boolean {
    if (!billingClient.isReady) return false
    val result = billingClient.isFeatureSupported(BillingClient.FeatureType.IN_APP_MESSAGING)
    return result.responseCode == BillingClient.BillingResponseCode.OK
}
```

# What does Play Billing ITEM_ALREADY_OWNED (7) mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/play-billing-item-already-owned.md
Description: ITEM_ALREADY_OWNED (7) means the user already owns the product. Query purchases, grant what they own and do not offer the product again.

Play Billing ITEM_ALREADY_OWNED (7) means the user already owns the subscription or one-time product they tried to buy.

## Quick facts

| | |
|---|---|
| Error | `BillingClient.BillingResponseCode.ITEM_ALREADY_OWNED` (7) |
| Where | Google Play Billing Library (`BillingResult.responseCode`) |
| What the vendor says | The purchase failed because the item is already owned. |

## Cause

- Google says the Google Play user already owns the product. In most cases this is not transient, except when stale purchase data cached by Play causes it.
- A stale cache is refreshed when you receive the error, so a retry after the refresh can succeed.
- Your app offered a product the user owns because it did not check what the user already has.

## Fix

1. Call `queryPurchasesAsync()` after the error to see what the user owns, and process those purchases (grant access, acknowledge or consume).
2. If the user does not own the product after that, retry the purchase once; the cache has been updated.
3. Prevent it: check the user's entitlements when you list products, and do not offer products the user already owns.
4. Tell the person "You already have this" instead of showing a failure.

## Example


Description: SERVICE_DISCONNECTED (-1) means the app lost its connection to the Play Store service. Enable automatic reconnection, check isReady and retry with backoff.

## Quick facts

| | |
|---|---|
| Error | `BillingClient.BillingResponseCode.SERVICE_DISCONNECTED` (-1) |

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/play-billing-service-timeout.md
Description: SERVICE_TIMEOUT (-3) means Google Play did not answer before the request timed out. Only Billing Library 5.2.0 and earlier return it; retry the same call, with backoff in the background.

Play Billing SERVICE_TIMEOUT (-3) means a request reached its maximum timeout before Google Play could answer.

## Quick facts

| | |
|---|---|
| Error | `BillingClient.BillingResponseCode.SERVICE_TIMEOUT` (-3) |
| Where | Google Play Billing Library (`BillingResult.responseCode`) |
| What the vendor says | The request has reached the maximum timeout before Google Play responds. |

## Cause

- Google gives an example: a delay in executing the action that the Billing Library call asked for.
- Only Billing Library 5.2.0 and earlier return it. From 6.0.0 `SERVICE_UNAVAILABLE` is returned for the same problem and `SERVICE_TIMEOUT` is deprecated.

## Example

```kotlin
import com.android.billingclient.api.BillingResult

suspend fun <T> retryOnTimeout(maxTries: Int = 3, call: suspend () -> Pair<BillingResult, T>): Pair<BillingResult, T> {

        delay(2_000L * tries)
        result = call()
        tries++
    }
    return result
}
```

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/sdk-configuration-error.md
Description: configurationError (code 23) means your setup does not line up: no offering product could be fetched from the store, or the backend said the platform is invalid (7000).

## Quick facts

# What does networkError (code 10) mean in the purchases SDK?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/sdk-network-error.md
Description: networkError (code 10) means a request could not finish on the network: a timeout, a dropped connection or an unreachable host. It is temporary, so retry after a pause.

The purchases SDK raises networkError (code 10) when a request fails at the network layer.

## Quick facts

| | |
|---|---|
| Error | `ErrorCode.networkError` (iOS), `PurchasesErrorCode.NetworkError` (Android), code 10 |
| Where | Purchases SDK (iOS, Android and the hybrid SDKs built on them) |
| What the vendor says | A network error has occurred. |

## Cause

- iOS: any `URLSession` failure other than "not connected to the Internet" (which becomes `offlineConnectionError`) maps here.
- Android: an `IOException` or `JSONException` while performing the request, and Play Billing `NETWORK_ERROR`.
- A wrong proxy URL: a typo, `http` instead of `https`, a missing port, or `localhost` on an Android emulator, where `localhost` is the emulator itself.

## Fix

1. Retry after a short wait and back off if it fails again.
2. Set the proxy URL before `configure`. On an Android emulator use `http://10.0.2.2:8787` for a server on your computer, or HTTPS.
3. On iOS, call `PurchasesDiagnostics.default.testSDKHealth()` to see whether the SDK can reach the server.
4. Read the underlying error: on iOS `NSUnderlyingErrorKey` holds the `URLError` with the real reason.

## Example

```swift
// The purchases SDK throws `ErrorCode` values; match the one you handle and let the rest fall through.
func handle(_ error: Error) {

        print("Not a purchases SDK error: \(error)")

        // Retrying is safe: the SDK keeps unposted purchases and sends them again later.
        print("Network problem; try again soon")
    default:
        print("Other purchases error: \(code.description)")
    }
}
```

# What does productAlreadyPurchasedError (code 6) mean in the purchases SDK?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/sdk-product-already-purchased-error.md
Description: productAlreadyPurchasedError (code 6) means the customer already owns the product. Refresh customer info or restore purchases instead of selling it again.

The purchases SDK raises productAlreadyPurchasedError (code 6) when the store refuses to sell a product the customer already owns.

## Quick facts

| | |
|---|---|
| Error | `ErrorCode.productAlreadyPurchasedError` (iOS), `PurchasesErrorCode.ProductAlreadyPurchasedError` (Android), code 6 |
| Where | Purchases SDK (iOS, Android and the hybrid SDKs built on them) |
| What the vendor says | This product is already active for the user. |

## Cause

- Android: Play Billing `ITEM_ALREADY_OWNED`. Google says it is usually permanent but can be stale cache, and recommends `queryPurchasesAsync()`.
- StoreKit 1: an `unknown` `SKError` whose underlying error says the customer is currently subscribed.
- On Android, the backend answered 7852 (a web purchase that belongs to another user); iOS reports that as `purchaseBelongsToOtherUser` instead.

1. Call `getCustomerInfo` and check the entitlement. If it is active, close the paywall.
2. If it is not active, call `restorePurchases()` so the SDK posts the owned purchase.
3. On Android, acknowledge or consume purchases so they do not stay owned and block a second purchase.
4. Hide the buy button for owners by checking the entitlement before you show the paywall.

# What does signatureVerificationFailed (code 37) mean in the purchases SDK?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/sdk-signature-verification-failed.md
Description: signatureVerificationFailed (code 37 on iOS, 36 on Android) means a response failed the SDK's signature check. It is thrown only when verification is enforced.

The purchases SDK raises signatureVerificationFailed (code 37 on iOS, 36 on Android) when a response fails the signature check and verification is enforced.

## Quick facts

| | |
|---|---|
| Error | `ErrorCode.signatureVerificationFailed` (iOS), `PurchasesErrorCode.SignatureVerificationError` (Android), code 37 |
| Where | Purchases SDK (iOS, Android and the hybrid SDKs built on them) |
| What the vendor says | Request failed signature verification. |

## Cause

- iOS: a response failed verification while the SDK was in enforced mode. In any other mode the SDK logs the failure and carries on.
- Android: a `SignatureVerificationException` becomes `SignatureVerificationError`, numbered 36 on Android and 37 on iOS.
- A server that does not sign with the key the SDK trusts. The stock SDK trusts only RevenueCat's key, and a proxy that rewrites responses breaks the signature too.

## Fix

1. Turn verification off in the SDK configuration (disabled mode). Native iOS and Android default to informational mode, which only logs a failure.
2. Never use enforced mode with the stock SDK against RevenueDot: it would reject every response.
3. Or build the RevenueDot forks with your server's public signing key to get verified responses.
4. Compare the key at `GET /.well-known/revenuedot-signing-key` with the key in your SDK build.

## Example

```swift

func handle(_ error: Error) {
    guard let code = error as? ErrorCode else {
        print("Not a purchases SDK error: \(error)")
        return
    }
    switch code {
    case .signatureVerificationFailed:
        // In informational mode nothing is thrown; with enforcement on, never unlock from this response.
        print("Signature verification failed")
    default:
        print("Other purchases error: \(code.description)")
    }
}
```

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/sdk-store-problem-error.md
Description: storeProblemError (code 2) means the App Store, Google Play or the payment system failed the request. It is usually temporary: retry once and read the underlying error.

The purchases SDK raises storeProblemError (code 2) when the App Store or Google Play fails a request or the backend reports a store problem.

## Quick facts

| | |
|---|---|
| Error | `ErrorCode.storeProblemError` (iOS), `PurchasesErrorCode.StoreProblemError` (Android), code 2 |
| Where | Purchases SDK (iOS, Android and the hybrid SDKs built on them) |
| What the vendor says | There was a problem with the store. |

3. Check that the store account on the device works: open the App Store or Google Play once and try again.
4. If the backend sent 7101, fix the store key or service account the message names, using Verify credentials on the app page.

```swift
    default:
        print("Other purchases error: \(code.description)")
    }
}
```

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/sdk-unknown-error.md
Description: unknownError (code 0) is the purchases SDK's catch-all for a failure it cannot classify. Read the underlying error, turn on debug logs and update the SDK.

The purchases SDK raises unknownError (code 0) when a failure matches none of its named errors.

## Quick facts

| | |
|---|---|
| Error | `ErrorCode.unknownError` (iOS), `PurchasesErrorCode.UnknownError` (Android), code 0 |
| Where | Purchases SDK (iOS, Android and the hybrid SDKs built on them) |

# What does StoreKitError.invalidPresentationContext mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-error-invalid-presentation-context.md
Description: StoreKitError.invalidPresentationContext means StoreKit cannot show its UI from the current context. Call StoreKit views and sheets from a visible scene on the main actor. Available from iOS 27.

StoreKitError.invalidPresentationContext means StoreKit tried to show its own screen and could not, because the context it was given cannot present one.

## Quick facts

| | |
|---|---|
| Error | `StoreKitError.invalidPresentationContext` |
| Where | StoreKit 2, Swift (`StoreKitError`) |
| Available since | iOS 27.0, iPadOS 27.0, macOS 27.0, tvOS 27.0, watchOS 27.0, visionOS 27.0 |
| What the vendor says | StoreKit UI cannot be presented from the current context. |

## Cause

- Apple's case page gives only that one line. The case is listed under the enumeration cases of `StoreKitError`, separate from the other error codes.

4. Retry after the scene is visible again, and show a short message if it still fails.

```swift
import StoreKit

func describe(_ error: Error) -> String {
```

# What does StoreKitError.networkError mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-error-network-error.md
Description: StoreKitError.networkError wraps the URLError behind a failed StoreKit 2 request. Read the URLError code, retry once the connection returns, and see how the SDK maps it.

StoreKitError.networkError means a StoreKit 2 request could not finish because of a network problem, and it carries the underlying `URLError`.

## Quick facts

| | |
|---|---|
| Error | `StoreKitError.networkError(URLError)` |
| Where | StoreKit 2, Swift (`StoreKitError`) |
| Available since | iOS 15.0, iPadOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, visionOS 1.0 |
| What the vendor says | A network error occurred. |

## Cause

- A StoreKit 2 request to the App Store failed at the network layer. The case carries a `URLError`, so the real reason (offline, timeout, lost connection) is in its `code`.
- Apple's documentation for the case is one line. The reason is not in the case name; it is in the associated `URLError`.
- The error comes from the device or its connection, not from your app's product configuration.

## Fix

1. Read `urlError.code` first. `.notConnectedToInternet` means the device is offline; `.timedOut` and `.networkConnectionLost` are usually temporary.
2. Retry the action after a short pause, or when the connection returns. Do not retry in a tight loop.
3. Show a message such as "Check your connection and try again" and keep the paywall open.
4. Do not unlock content because of this error. Unlock from verified transactions only.

## Example

```swift
import StoreKit

// A purchase that fails on the network is safe to offer again: nothing was bought.
func buy(_ product: Product) async {
    do {
        let result = try await product.purchase()
        print("Purchase result: \(result)")
    } catch StoreKitError.networkError(let urlError) {
        // The URLError code says why: offline, timeout, lost connection.
        print("Network problem (\(urlError.code.rawValue)); ask the person to try again")
    } catch {
        print("Purchase failed: \(error)")
    }
}
```

# What does StoreKitError.notAvailableInStorefront mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-error-not-available-in-storefront.md
Description: StoreKitError.notAvailableInStorefront means a StoreKit 2 call is not available on a device whose App Store storefront does not support it. Causes, fix and a Swift example.

StoreKitError.notAvailableInStorefront means StoreKit 2 refused a function because the device's App Store storefront does not support it.

## Quick facts

| | |
|---|---|
| Error | `StoreKitError.notAvailableInStorefront` |
| Where | StoreKit 2, Swift (`StoreKitError`) |
| Available since | iOS 15.0, iPadOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, visionOS 1.0 |
| What the vendor says | The function is not available on devices configured for this storefront. |

## Cause

- The device's App Store country or region (its storefront) is one where the requested function is not offered. Apple documents the case in one line and does not publish a list of the calls or storefronts that trigger it.
- In-app products you create in App Store Connect are sold per region, and Apple says you keep your own list of product identifiers and the storefronts where you want them available ([Storefront](https://developer.apple.com/documentation/storekit/storefront)).
- In the sandbox, changing the App Store Country or Region of a Sandbox Apple Account changes the storefront your app sees, so a tester can hit this error after a region change ([Storefront](https://developer.apple.com/documentation/storekit/storefront)).

## Fix

1. Read the storefront with `Storefront.current` and log its `countryCode` next to the error, so you know which region failed.
2. Check in App Store Connect that the product's availability includes that region, and check the app's own availability too.
3. Do not retry in a loop. The same call fails the same way until the storefront or the availability changes. Hide the product or show a short "not available in your region" message instead.
4. To reproduce it, change the region of a Sandbox Apple Account and run the same call again.

## Example

```swift
import StoreKit

// Load products, and explain a storefront problem instead of retrying: the same call keeps failing in that region.
func loadProducts(ids: [String]) async -> [Product] {
    do {
        return try await Product.products(for: ids)
    } catch StoreKitError.notAvailableInStorefront {
        // Log the region so support can tell a storefront problem from a network problem.
        let region = await Storefront.current?.countryCode ?? "unknown"
        print("StoreKit says this function is not available in storefront \(region)")
        return []
    } catch {
        print("Could not load products: \(error)")
        return []
    }
}
```

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-error-system-error.md
Description: StoreKitError.systemError means the system failed a StoreKit 2 call, and it wraps the underlying error. How to read it, what to retry and how the SDK maps it.

## Quick facts

| Available since | iOS 15.0, iPadOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, visionOS 1.0 |
| What the vendor says | A system error occurred. |

## Cause

- The system, not your app's request, failed the operation. The case carries the underlying `Error`, which is the only place the detail lives.

```swift
    } catch StoreKitError.systemError(let underlying) {

        print("StoreKit system error: domain \(ns.domain), code \(ns.code), \(ns.localizedDescription)")
    } catch {
        print("Other error: \(error)")
    }
}
```

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-error-unsupported.md

# What does StoreKitError.userCancelled mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-error-user-cancelled.md
Description: StoreKitError.userCancelled means the person cancelled a StoreKit 2 flow. It is not a failure: show no error and leave the paywall as it was.

StoreKitError.userCancelled means the person cancelled, so nothing was bought and nothing is broken.

## Quick facts

| | |
|---|---|
| Error | `StoreKitError.userCancelled` |
| Where | StoreKit 2, Swift (`StoreKitError`) |
| Available since | iOS 15.0, iPadOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, visionOS 1.0 |
| What the vendor says | The user canceled. |

## Cause

- The person dismissed a StoreKit flow, such as the purchase confirmation sheet, before finishing it.
- A purchase made with `Product.purchase()` reports a cancel as the result `Product.PurchaseResult.userCancelled`, which Apple documents as the user cancelling the purchase. The error case is the same outcome in error form, so handle both the same way.
- Apple documents no other cause. A cancel is the person's choice, not an App Store failure.

## Fix

1. Do not show an error. A cancel is a normal step in a purchase funnel.
2. Leave the paywall open with its products loaded, so the person can choose again.
3. Count cancels apart from failures in your analytics, so real errors stay visible.
4. Do not unlock anything and do not retry for the person.

## Example

```swift
import StoreKit

// Treat a cancel as an outcome, not an error: no alert, no retry, no unlock.
func buy(_ product: Product) async {
    do {
        switch try await product.purchase() {
        case .userCancelled:
            print("Cancelled by the person; leave the paywall as it is")
        case .pending:
            print("Waiting for approval; do not unlock yet")
        case .success(let verification):
            print("Bought: \(verification)")
        @unknown default:
            break
        }
    } catch StoreKitError.userCancelled {
        // The error form of the same outcome.
        print("Cancelled by the person; leave the paywall as it is")
    } catch {
        print("Purchase failed: \(error)")
    }
}
```

# What does Product.PurchaseError.ineligibleForOffer mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-purchase-error-ineligible-for-offer.md
Description: Product.PurchaseError.ineligibleForOffer means the customer is not eligible for the offer you applied. Check eligibility before you show an introductory or promotional offer.

Product.PurchaseError.ineligibleForOffer means the customer is not eligible for the offer that the purchase tried to use.

## Quick facts

| | |
|---|---|
| Error | `Product.PurchaseError.ineligibleForOffer` |
| Where | StoreKit 2, Swift (`Product.purchase(options:)`) |
| Available since | iOS 15.0, iPadOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, visionOS 1.0 |
| What the vendor says | The user is not eligible for the offer. |

## Cause

- Apple says the App Store treats customers with an existing or expired subscription in the app as eligible for a promotional offer. A customer without one is not eligible ([Implementing promotional offers](https://developer.apple.com/documentation/storekit/implementing-promotional-offers-in-your-app)).
- Introductory offers have their own rule: `isEligibleForIntroOffer` is true when the customer is eligible for an introductory offer on the subscription or on any subscription in the same group ([isEligibleForIntroOffer](https://developer.apple.com/documentation/storekit/product/subscriptioninfo/iseligibleforintrooffer)).
- A customer who already redeemed the introductory offer in that group is no longer eligible.

## Fix

1. Check eligibility before you show the offer: `Product.SubscriptionInfo.isEligibleForIntroOffer` for introductory offers, and your own rules plus the customer's subscription history for promotional offers.
2. Show the standard price when the customer is not eligible, instead of an offer that will fail.
3. Apple notes that eligibility can be true even when you have not set up an introductory offer, so also check that the offer exists on the product.
4. Do not retry. The result stays the same until the customer's eligibility changes.

## Example

```swift
import StoreKit

// Ask the App Store whether this customer can get the introductory offer before you advertise it.
func showPrice(for product: Product) async {
    guard let subscription = product.subscription else { return }
    let eligible = await subscription.isEligibleForIntroOffer
    print(eligible ? "Show the introductory offer" : "Show the standard price")
}

func buy(_ product: Product, options: Set<Product.PurchaseOption>) async {
    do {
        _ = try await product.purchase(options: options)
    } catch Product.PurchaseError.ineligibleForOffer {
        print("Not eligible for this offer; fall back to the standard price")
    } catch {
        print("Purchase failed: \(error)")
    }
}
```

# What does Product.PurchaseError.invalidOfferSignature mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-purchase-error-invalid-offer-signature.md
Description: Product.PurchaseError.invalidOfferSignature means the App Store rejected the signature of a promotional offer. Rebuild the signed text, use a fresh nonce and sign it with the right key.

Product.PurchaseError.invalidOfferSignature means the App Store could not validate the signature of the promotional offer.

## Quick facts

| | |
|---|---|
| Error | `Product.PurchaseError.invalidOfferSignature` |
| Where | StoreKit 2, Swift (`Product.purchase(options:)`) |
| Available since | iOS 15.0, iPadOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, visionOS 1.0 |
| What the vendor says | The offer signature is not valid. |

## Cause

- Apple says the signature is made from the product and offer parameters plus a nonce and timestamp your server generates, joined in a fixed order with the invisible separator U+2063, and signed with your PKCS #8 private key using ECDSA with SHA-256 ([Generating a signature](https://developer.apple.com/documentation/storekit/generating-a-signature-for-promotional-offers)).
- Apple also says each payload, signature and nonce is valid for one buy request only, even if the buy fails, so reusing a signature after a failed attempt fails.
- If you pass an app account token, Apple says it must be part of the signed text, and the UUID strings of the token and the nonce must be lowercase ([promotionalOffer option](https://developer.apple.com/documentation/storekit/product/purchaseoption/promotionaloffer%28offerid:keyid:nonce:signature:timestamp:%29)).

## Fix

1. Rebuild the signed string in the exact order Apple lists, with the separator between the parts.
2. Create a new nonce and timestamp for every attempt, and sign again after any failed purchase.
3. Sign with the private key whose key ID you send as `keyID`, and Base64-encode the DER signature.
4. Use lowercase UUID strings for the nonce and the app account token, and sign the same values you send.
5. Check the signature locally with the public key before you send it, as Apple suggests.

## Example

```swift
import StoreKit

// A signature works once. After a failed purchase, ask your server for a new nonce, timestamp and signature.
func buy(_ product: Product, offerID: String, keyID: String, nonce: UUID, signature: Data, timestamp: Int) async {
    let offer = Product.PurchaseOption.promotionalOffer(offerID: offerID, keyID: keyID, nonce: nonce, signature: signature, timestamp: timestamp)
    do {
        _ = try await product.purchase(options: [offer])
    } catch Product.PurchaseError.invalidOfferSignature {
        print("The App Store rejected the signature; request a fresh one from the server")
    } catch {
```

# What does Product.PurchaseError.missingOfferParameters mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-purchase-error-missing-offer-parameters.md
Description: Product.PurchaseError.missingOfferParameters means the offer parameters are missing from a purchase. Send the offer ID, key ID, nonce, signature and timestamp, or the signed JWS.

Product.PurchaseError.missingOfferParameters means the purchase named an offer but did not carry all the parameters the App Store needs to apply it.

## Quick facts

| | |
|---|---|
| Error | `Product.PurchaseError.missingOfferParameters` |
| Where | StoreKit 2, Swift (`Product.purchase(options:)`) |
| Available since | iOS 15.0, iPadOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, visionOS 1.0 |
| What the vendor says | The offer parameters are missing. |

## Cause

- Apple's case page gives only that one line. It lists no causes.
- A promotional offer needs several values: the offer ID, and either the key ID, nonce, signature and timestamp from your server, or a compact JWS signed on your server. The `promotionalOffer(offerID:keyID:nonce:signature:timestamp:)` option takes the first group.

## Fix

1. Build the offer option from one server response that contains every value, and pass nothing partial.
2. Move to the JWS option (`promotionalOffer(_:compactJWS:)`) when your minimum iOS version allows it. It carries the signed offer as one string.
3. Check that your server returns the key ID, the nonce, the timestamp and the signature, and that the app does not drop one while decoding.
4. Request a fresh signature for each attempt. A signature works for one purchase request only.

## Example

```swift
import StoreKit

struct SignedOffer {
    let offerID: String
    let keyID: String
    let nonce: UUID
    let signature: Data
    let timestamp: Int
}

func buy(_ product: Product, offer: SignedOffer) async {
    let option = Product.PurchaseOption.promotionalOffer(offerID: offer.offerID, keyID: offer.keyID, nonce: offer.nonce, signature: offer.signature, timestamp: offer.timestamp)
    do {
        _ = try await product.purchase(options: [option])
    } catch Product.PurchaseError.missingOfferParameters {
        print("An offer parameter is missing; request a complete signed offer from the server")
    } catch {
        print("Purchase failed: \(error)")
    }
}
```

# What does Product.PurchaseError.paymentMethodBindingConfigurationRequired mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-purchase-error-payment-method-binding-configuration-required.md
Description: paymentMethodBindingConfigurationRequired means the customer must add a payment method to their Apple Account before buying. Use PaymentMethodBinding to prompt them, then retry the purchase.

Product.PurchaseError.paymentMethodBindingConfigurationRequired means the customer has no payment method on their Apple Account, so they must add one before the purchase can go through.

## Quick facts

| | |
|---|---|
| Error | `Product.PurchaseError.paymentMethodBindingConfigurationRequired` |
| Where | StoreKit 2, Swift (`Product.purchase(options:)`) |
| Available since | iOS 26.5, iPadOS 26.5, macOS 26.5, tvOS 26.5, watchOS 26.5, visionOS 26.5 |
| What the vendor says | The customer needs to add a payment method to their Apple Account before making a purchase; use PaymentMethodBinding to prompt the customer and bind the payment method. |

## Cause

- Apple says the customer has no usable payment method on their Apple Account at the time of the purchase.
- `PaymentMethodBinding` is available only to eligible apps with server entitlements. Its initializer throws if the app lacks the entitlement or the person is not eligible ([PaymentMethodBinding](https://developer.apple.com/documentation/storekit/paymentmethodbinding)).
- The error exists from iOS 26.5, so older systems never throw it.

## Fix

1. Catch the error and start the binding flow: your server asks Apple for an in-app binding identifier, the app creates `PaymentMethodBinding(id:)` with it and calls `bind()`.
2. `bind()` shows the system prompt where the customer confirms the new payment method as their primary one. Retry the purchase when it returns.
3. If the initializer throws, the app or the customer is not eligible. Show a message that points to Settings and the Apple Account payment methods instead.
4. Guard the code with an availability check for iOS 26.5 and keep a generic error path for earlier versions.

## Example

```swift
import StoreKit

// When the customer has no payment method, bind one with the identifier your server got from Apple, then buy again.
@available(iOS 26.5, *)
func buy(_ product: Product, bindingID: () async -> String?) async {
    do {
        _ = try await product.purchase()
    } catch Product.PurchaseError.paymentMethodBindingConfigurationRequired {
        guard let id = await bindingID() else { return }
        do {
            let binding = try await PaymentMethodBinding(id: id)
            try await binding.bind()
            print("Payment method bound; buy again")
        } catch {
            print("Binding failed: \(error)")
        }
    } catch {
        print("Purchase failed: \(error)")
    }
}
```

# What does Transaction.RefundRequestError.duplicateRequest mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-refund-error-duplicate-request.md
Description: Transaction.RefundRequestError.duplicateRequest means the App Store already has a refund request for this purchase. Check the transaction first, then do not send it again.

Transaction.RefundRequestError.duplicateRequest means the App Store has already received a refund request for this In-App Purchase.

## Quick facts

| | |
|---|---|
| Error | `Transaction.RefundRequestError.duplicateRequest` |
| Where | StoreKit 2, Swift (`Transaction.beginRefundRequest`) |
| Available since | iOS 15.0, iPadOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, visionOS 1.0 |
| What the vendor says | The App Store has already received a refund request for this In-App Purchase. |

## Cause

- Apple says StoreKit returns this error when the App Store already holds a refund request for the transaction and the decision is still pending, was denied or was approved.
- The person (or your code) called `beginRefundRequest` for a transaction that already has a request. Sending it again cannot change the outcome.
- Apple suggests checking the transaction's refund state before you call the method, to see whether the App Store has already refunded it.

## Fix

1. Before you offer a refund request, check the transaction's `revocationDate` and `revocationReason`. If the App Store has already refunded the purchase there is nothing to request.
2. Tell the person a request already exists, and that Apple makes the decision.
3. Do not call the method again for the same transaction.
4. Test refund requests in the sandbox or in Xcode first, as Apple's refund testing guide describes.

## Example

```swift
import StoreKit
import UIKit

// A second request for the same transaction cannot work: say so, and stop.
@MainActor
func requestRefund(productID: String, in scene: UIWindowScene) async {
    guard let result = await Transaction.latest(for: productID), case .verified(let transaction) = result else { return }
    // Apple suggests checking the refund state first: a revoked transaction is already refunded.
    if transaction.revocationDate != nil {
        print("The App Store already refunded this purchase")
        return
    }
    do {
        let status = try await transaction.beginRefundRequest(in: scene)
        print("Refund request status: \(status)")
    } catch Transaction.RefundRequestError.duplicateRequest {
        print("A refund request for this purchase already exists; Apple decides it")
    } catch {
        print("Refund request failed: \(error)")
    }
}
```

# What does Transaction.RefundRequestError.failed mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-refund-error-failed.md
Description: Transaction.RefundRequestError.failed means a StoreKit 2 refund request could not be submitted, for example because the transaction ID is not valid. Check the ID and the verified transaction.

Transaction.RefundRequestError.failed means the App Store could not take the refund request you submitted.

## Quick facts

| | |
|---|---|
| Error | `Transaction.RefundRequestError.failed` |
| Where | StoreKit 2, Swift (`Transaction.beginRefundRequest(in:)`) |
| Available since | iOS 15.0, iPadOS 15.0, macOS 12.0, tvOS 17.0, watchOS 10.0, visionOS 1.0 |
| What the vendor says | The refund request submission failed. |

## Cause

- Apple says a submission can fail for many reasons, such as an invalid transaction identifier, or because the App Store cannot process the request for another reason.
- It is different from `duplicateRequest`, which means a request for the transaction already exists.
- The refund sheet needs a transaction the App Store knows, so passing the ID of an unverified or unrelated transaction fails.

1. Get the transaction with `Transaction.latest(for:)` and only offer the request for a `.verified` result.
2. Pass that transaction's own `id` and a scene that is on screen.
3. Tell the person the request could not be sent and let them try again later. Retrying at once is unlikely to help.
4. Log the error and transaction ID. Refund requests can be tested in the sandbox, as Apple's refund testing guide describes.

## Example

```swift
import StoreKit
import UIKit

// A failed submission: say so, and offer a later retry.
@MainActor
func requestRefund(productID: String, in scene: UIWindowScene) async {
    guard let result = await Transaction.latest(for: productID), case .verified(let transaction) = result else {
        print("No verified transaction to refund")
        return
    }
    do {
        let status = try await transaction.beginRefundRequest(in: scene)
        print("Refund request status: \(status)")
    } catch Transaction.RefundRequestError.failed {
        print("The refund request could not be submitted; try again later")
    } catch {
        print("Refund request error: \(error)")
    }
}
```

# What does VerificationError.invalidCertificateChain mean in StoreKit 2?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/errors/storekit-verification-error-invalid-certificate-chain.md
Description: VerificationResult.VerificationError.invalidCertificateChain means the certificate chain of a signed StoreKit 2 value is not valid. Treat the transaction as untrusted, log the reason and verify it on your server before unlocking.

VerificationResult.VerificationError.invalidCertificateChain means the certificate chain of a signed StoreKit 2 value is not valid.

## Quick facts

| | |
|---|---|
| Error | `VerificationResult.VerificationError.invalidCertificateChain` |
| Where | StoreKit 2, Swift (`VerificationResult`) |
| Available since | iOS 15.0, iPadOS 15.0, macOS 12.0, tvOS 15.0, watchOS 8.0, visionOS 1.0 |
| What the vendor says | An error indicating that the certificate chain is invalid. |

## Cause

- StoreKit 2 returns transactions, renewal information and the app transaction wrapped in a `VerificationResult`. It checks them for you, and a value that fails is `.unverified` with the reason as a `VerificationError` ([VerificationResult](https://developer.apple.com/documentation/storekit/verificationresult)).
- Apple says this can happen when one or more certificates in the chain are expired or come from an untrusted source.
- `invalidCertificateChain` is one of six reasons Apple lists, next to `invalidSignature`, `invalidCertificateChain`, `invalidDeviceVerification`, `invalidEncoding`, `missingRequiredProperties` and `revokedCertificate`.

## Fix

1. Treat an `.unverified` result as untrusted. Do not unlock content from it and do not call `finish()` on it until you have decided what to do.
2. If the device clock is wrong, ask the person to set date and time automatically, because expired-looking certificates are a common result.
3. Log the `VerificationError` and the transaction ID, then check the same transaction on your server with Apple's App Store Server Library or the App Store Server API.
4. If it only happens in testing, check the test environment (Xcode StoreKit configuration, sandbox account) before changing code.

## Example

```swift
import StoreKit

// Only a verified transaction may unlock content. Log the reason when a transaction is unverified.
func handle(_ result: VerificationResult<Transaction>) {
    switch result {
    case .verified(let transaction):
        print("Unlock \(transaction.productID)")
    case .unverified(let transaction, let error):
        if case .invalidCertificateChain = error {
            print("The certificate chain is invalid for \(transaction.productID); do not unlock")
        } else {
            print("Verification failed: \(error)")
        }
    }
}
```
