# What does the App Store notification CONSUMPTION_REQUEST mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-consumption-request.md
Description: CONSUMPTION_REQUEST means a customer asked Apple for a refund and Apple wants usage data from you. RevenueDot's Refund Control can answer it.

The App Store notification CONSUMPTION_REQUEST means a customer asked for a refund and Apple wants you to report how much of the purchase they used.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `CONSUMPTION_REQUEST` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | The customer started a refund request for a consumable or an auto-renewable subscription, and the App Store asks you for consumption data. |

## What triggers it

- The customer asked for a refund through Apple. Apple then asks the developer for facts about the purchase before it decides.
- It applies to consumable in-app purchases and auto-renewable subscriptions.
- Apple makes the final decision, and tells you with `REFUND` or `REFUND_DECLINED`.

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. Answer with the Send Consumption Information endpoint of the App Store Server API, and only when you have the customer's consent to share the data.
3. Base your answer on facts: how much they used, whether they were a paying customer, and your refund preference.
4. Wait for `REFUND` or `REFUND_DECLINED` for the result.
5. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"CONSUMPTION_REQUEST","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  if (n.notificationType !== "CONSUMPTION_REQUEST") return "ignore";
  const consented = true;
  return consented ? "send consumption information to Apple" : "skip, no customer consent";
}

console.log(decide(notification));
```

## How RevenueDot handles it

RevenueDot verifies Apple's signature, checks the bundle ID, stores the notification and answers 200. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. # What does the App Store notification DID_CHANGE_RENEWAL_PREF mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-did-change-renewal-pref.md
Description: DID_CHANGE_RENEWAL_PREF means the customer changed their subscription plan. UPGRADE starts now, DOWNGRADE at the next renewal, and no subtype means they reverted a downgrade.

The App Store notification DID_CHANGE_RENEWAL_PREF means the customer switched to a different subscription plan in the same group.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `DID_CHANGE_RENEWAL_PREF` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | The customer changed their subscription plan. UPGRADE takes effect immediately, DOWNGRADE at the next renewal date, and an empty subtype means the customer reverted to the current plan, cancelling a downgrade. |

## What triggers it

- Subtype `UPGRADE`: the upgrade takes effect at once and starts a new billing period. Apple gives the customer a prorated refund for the unused part of the old period.
- Subtype `DOWNGRADE`: the change takes effect at the next renewal date and does not affect the active plan. A cross-grade to a different duration counts as a downgrade.
- No subtype: the customer changed the renewal preference back to the current plan, which cancels a scheduled downgrade.

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. On `UPGRADE`, switch the entitlement now, to the product in the new transaction.
3. On `DOWNGRADE`, keep the current plan and note the product in `autoRenewProductId` of the renewal info as the plan from the next renewal.
4. With no subtype, clear the scheduled change.
5. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"DID_CHANGE_RENEWAL_PREF","subtype":"UPGRADE","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  if (n.notificationType !== "DID_CHANGE_RENEWAL_PREF") return "ignore";
  if (n.subtype === "UPGRADE") return "switch plan now";
  if (n.subtype === "DOWNGRADE") return "switch plan at the next renewal";
  return "clear the scheduled downgrade";
}

console.log(decide(notification));
```

## How RevenueDot handles it

A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. The renewal info's `autoRenewProductId` is stored. A downgrade scheduled for the next renewal gives `PRODUCT_CHANGE` with `new_product_id` set to that product. An upgrade arrives as a transaction for the new product, which gives `PRODUCT_CHANGE` with `product_id` the old product, plus `RENEWAL` when the new product starts a new period.

# What does the App Store notification DID_CHANGE_RENEWAL_STATUS with subtype AUTO_RENEW_DISABLED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-did-change-renewal-status-auto-renew-disabled.md
Description: DID_CHANGE_RENEWAL_STATUS with subtype AUTO_RENEW_DISABLED means the customer cancelled, or Apple turned auto-renew off after a refund request. Keep access to the period end.

The App Store subtype AUTO_RENEW_DISABLED means auto-renew was turned off for a subscription that has not expired yet.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `DID_CHANGE_RENEWAL_STATUS`, `subtype` `AUTO_RENEW_DISABLED` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | The customer turned off subscription auto-renewal, or the App Store turned it off after the customer requested a refund. |

## What triggers it

- The customer cancelled in the App Store Subscriptions settings.
- The system turned auto-renew off because the customer started a refund request through your app with the refund request API.
- The subscription itself is not over: it expires at the end of the paid period and `EXPIRED` with subtype `VOLUNTARY` follows then.

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. Keep access until `expiresDate`.
3. Show a message that the subscription ends on that date, and offer a way back.
4. Do not mark the customer as churned until `EXPIRED` arrives.
5. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"DID_CHANGE_RENEWAL_STATUS","subtype":"AUTO_RENEW_DISABLED","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  const off = n.notificationType === "DID_CHANGE_RENEWAL_STATUS" && n.subtype === "AUTO_RENEW_DISABLED";
```

# What does the App Store notification DID_CHANGE_RENEWAL_STATUS mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-did-change-renewal-status.md
Description: DID_CHANGE_RENEWAL_STATUS means the customer turned auto-renew off (AUTO_RENEW_DISABLED) or on (AUTO_RENEW_ENABLED). Access continues to the end of the paid period.

The App Store notification DID_CHANGE_RENEWAL_STATUS means the customer changed whether their subscription renews automatically.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `DID_CHANGE_RENEWAL_STATUS` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | The customer changed the subscription's renewal status. AUTO_RENEW_ENABLED means auto-renew was turned on; AUTO_RENEW_DISABLED means it was turned off, by the customer or by the App Store after a refund request. |

## What triggers it

- Subtype `AUTO_RENEW_DISABLED`: the customer cancelled from the App Store Subscriptions page, or the App Store turned off auto-renew after the customer started a refund through your app's refund request API.
- Subtype `AUTO_RENEW_ENABLED`: the customer subscribed again after cancelling, which turns auto-renew back on.
- Apple also sends it without a subtype when the customer cancels after a price increase notice.

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. Keep access until `expiresDate`: the customer paid for the period.
3. On `AUTO_RENEW_DISABLED`, start your win-back flow. Apple suggests this notification as one input for deciding who is eligible for a promotional offer.
4. On `AUTO_RENEW_ENABLED`, stop the win-back flow.
5. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"DID_CHANGE_RENEWAL_STATUS","subtype":"AUTO_RENEW_DISABLED","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  if (n.notificationType !== "DID_CHANGE_RENEWAL_STATUS") return "ignore";
  if (n.subtype === "AUTO_RENEW_DISABLED") return "keep access to the end of the period, start win-back";
  if (n.subtype === "AUTO_RENEW_ENABLED") return "stop win-back";
  return "check the renewal info";
}

console.log(decide(notification));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `start win-back` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot verifies Apple's signature, checks the bundle ID, stores the notification and answers 200. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. Type overrides set auto-renew from the subtype. Turning it off gives a `CANCELLATION` event with `cancel_reason: UNSUBSCRIBE` (or the store's reason, or `BILLING_ERROR` when a billing issue exists); turning it back on gives `UNCANCELLATION`. Description: DID_FAIL_TO_RENEW means a renewal failed because of a billing issue and the subscription entered billing retry. With subtype GRACE_PERIOD keep access; otherwise stop it and ask for new billing details.

The App Store notification DID_FAIL_TO_RENEW means a subscription failed to renew because of a billing issue and entered the billing retry period.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `DID_FAIL_TO_RENEW` |

```javascript
  return n.subtype === "GRACE_PERIOD" ? "keep access, ask the customer to fix billing" : "stop access, ask the customer to fix billing";
```

# What does the App Store notification REFUND_REVERSED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-refund-reversed.md
Description: REFUND_REVERSED means Apple reversed a refund after a customer dispute. Reinstate the access or item you revoked. A subscription's renewal date does not change.

The App Store notification REFUND_REVERSED means Apple took back a refund it had granted, after a dispute by the customer.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `REFUND_REVERSED` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | The App Store reversed a refund it granted, because of a dispute the customer raised. If your app revoked content because of the refund, it needs to restore it. |

## What triggers it

- The customer disputed a refund and Apple reversed it.
- It applies to every product type. For auto-renewable subscriptions the renewal date stays the same.
- You will have seen a `REFUND` for the same transaction earlier.

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. Restore the access or credited item that the refund removed.
3. Undo the refund record on your side so revenue reports match.
4. Match it to the earlier `REFUND` by `transactionId`.
5. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"REFUND_REVERSED","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  if (n.notificationType !== "REFUND_REVERSED") return "ignore";
  return "reinstate the purchase, remove the refund record";
}

console.log(decide(notification));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `reinstate the purchase` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot verifies Apple's signature, checks the bundle ID, stores the notification and answers 200. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. The transaction no longer has a revocation date, so the refund time is cleared and RevenueDot sends `REFUND_REVERSED`. Its payload adds `renewal_number`, the count of renewals the subscription had gone through, as RevenueCat's sample does.

# What does the App Store notification REFUND mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-refund.md
Description: REFUND means the App Store refunded a purchase. Revoke what the customer got, using the revocation date and reason. Applies to consumables, non-consumables and subscriptions.

The App Store notification REFUND means Apple refunded a transaction, so the customer should lose what that purchase gave them.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `REFUND` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | The App Store refunded a transaction for a consumable, a non-consumable, an auto-renewable subscription or a non-renewing subscription. revocationDate holds the time of the refund. |

## What triggers it

- Apple approved a refund request, whether the customer asked through Apple support or through your app's refund request API.
- The decoded transaction has `revocationDate` and `revocationReason`, and `originalTransactionId` and `productId` identify the purchase.
- Apple's Get Refund History endpoint lists a customer's refunded transactions.

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. Revoke the access or the credited item for that transaction, effective at `revocationDate`.
3. Keep a record of the refund against the customer for support.
4. Only roll back what that transaction gave: a refund of an old renewal does not undo the current period.
5. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"REFUND","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  if (n.notificationType !== "REFUND") return "ignore";
  const revokedAt = 1790800914000;
  return "revoke the purchase as of " + new Date(revokedAt).toISOString().slice(0, 10);
}

console.log(decide(notification));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `revoke the purchase as of 2026-09-30` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot verifies Apple's signature, checks the bundle ID, stores the notification and answers 200. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. The transaction's `revocationDate` becomes the purchase's refund time. A refunded subscription period gives `CANCELLATION` with `cancel_reason: CUSTOMER_SUPPORT` and a negative price. A refund of an older period never rolls the chain back, because RevenueCat reports only the latest period. If the transaction had a refund request, Refund Control marks it approved.

# What does the App Store notification RENEWAL_EXTENDED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-renewal-extended.md
Description: RENEWAL_EXTENDED means the App Store pushed one subscription's renewal date back, as you asked through the Server API. Extend access to the new date.

The App Store notification RENEWAL_EXTENDED means Apple moved one subscription's renewal date later, at your request.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `RENEWAL_EXTENDED` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | The App Store extended the renewal date of a specific subscription, after you called Extend a Subscription Renewal Date or Extend Subscription Renewal Dates for All Active Subscribers. |

## What triggers it

- Your server called Extend a Subscription Renewal Date in the App Store Server API for this customer.
- Or your server called the bulk endpoint and this subscriber's extension succeeded.
- The paid period is unchanged; only the end date moves.

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. Read the new `expiresDate` from `signedTransactionInfo` and extend access to it.
3. Record why the extension was given, such as a service outage or a goodwill gesture.
4. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"RENEWAL_EXTENDED","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  if (n.notificationType !== "RENEWAL_EXTENDED") return "ignore";
  return "extend access to the new expiresDate";
}

console.log(decide(notification));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `extend access` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot verifies Apple's signature, checks the bundle ID, stores the notification and answers 200. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. The new `expiresDate` is applied to the stored purchase. When the period start is unchanged and the end moves later, RevenueDot sends `SUBSCRIPTION_EXTENDED`.

# What does the App Store notification RENEWAL_EXTENSION mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-renewal-extension.md
Description: RENEWAL_EXTENSION reports a bulk renewal-date extension: subtype SUMMARY when it finished for all subscribers, FAILURE when one subscription failed. Log it and retry failures.

The App Store notification RENEWAL_EXTENSION reports how a bulk renewal-date extension went: a SUMMARY when it finished, a FAILURE for one subscription that failed.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `RENEWAL_EXTENSION` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | The App Store is attempting the renewal-date extension you asked for with Extend Subscription Renewal Dates for All Active Subscribers. SUMMARY means it finished for all eligible subscribers; FAILURE means it failed for one subscription. |

## What triggers it

- Your server called the bulk extension endpoint in the App Store Server API.
- Subtype `SUMMARY`: the work is done. The `summary` object holds the details instead of `data`.
- Subtype `FAILURE`: one subscription was not extended. See the `data` object.

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. On `SUMMARY`, compare the counts with what you expected and log them.
3. On `FAILURE`, note the subscription and try the single-subscription extension for it, or tell the customer.
4. Do not change any customer's access because of this type: individual successes arrive as `RENEWAL_EXTENDED`.
5. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"RENEWAL_EXTENSION","subtype":"SUMMARY","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  if (n.notificationType !== "RENEWAL_EXTENSION") return "ignore";
  return n.subtype === "SUMMARY" ? "log the summary counts" : "retry the failed subscription";
}

console.log(decide(notification));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `log the summary counts` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot verifies Apple's signature, checks the bundle ID, stores the notification and answers 200. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. RevenueDot stores the notification and marks the app's notifications as received, and changes no purchase: this type is not in the list that updates purchases. Individual extensions arrive as `RENEWAL_EXTENDED`.

# What does the App Store notification REVOKE mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-revoke.md
Description: REVOKE means a Family Sharing entitlement is no longer available: sharing was turned off, a family member left, or the purchaser got a refund. Remove the family member's access.

The App Store notification REVOKE means a purchase that a family member could use through Family Sharing is no longer shared with them.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `REVOKE` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | An in-app purchase the customer had through Family Sharing is no longer available that way. The App Store sends it when the purchaser turns off Family Sharing for it, when the purchaser or a family member leaves the family, or when the purchaser is refunded. |

## What triggers it

- The purchaser disabled Family Sharing for the purchase.
- The purchaser or the family member left the family group.
- The purchaser received a refund. Family Sharing applies to non-consumables and auto-renewable subscriptions.

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. Remove the family member's access to that purchase, and keep the purchaser's own access.
3. On iOS the app also gets `paymentQueue(_:didRevokeEntitlementsForProductIdentifiers:)` for StoreKit 1 apps. A StoreKit 2 app sees the transaction's `revocationDate`.
4. Offer the family member their own subscription.
5. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"REVOKE","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  if (n.notificationType !== "REVOKE") return "ignore";
  return "remove the family member's access, keep the purchaser's";
}

console.log(decide(notification));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `remove the family member's access` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot verifies Apple's signature, checks the bundle ID, stores the notification and answers 200. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. REVOKE is one of the types that apply the signed transaction. RevenueDot reads the transaction's `revocationDate` as the refund time, so the stored purchase is treated like a refunded one and a `CANCELLATION` event with `cancel_reason: CUSTOMER_SUPPORT` follows.

# What does the App Store notification SUBSCRIBED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-subscribed.md
Description: SUBSCRIBED means a customer subscribed to an auto-renewable subscription. Subtype INITIAL_BUY is the first time, RESUBSCRIBE a return. Grant access and record the purchase.

The App Store notification SUBSCRIBED means a customer subscribed to an auto-renewable subscription, for the first time or again.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `SUBSCRIBED` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | The customer subscribed to an auto-renewable subscription. The subtype says whether it is the first purchase or a resubscribe. |

## What triggers it

- Subtype `INITIAL_BUY`: the customer bought or got access through Family Sharing to a subscription in the group for the first time, including by redeeming an offer code.
- Subtype `RESUBSCRIBE`: the customer resubscribed, or got access through Family Sharing, to the same subscription or another one in the same subscription group, including through a promotional, offer code or win-back offer.
- To tell whether an offer was used, Apple says to check `offerType` in the decoded transaction (`JWSTransactionDecodedPayload`).

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. Decode `signedTransactionInfo`, find the customer through your own account link (for example the `appAccountToken`) and grant the entitlement until `expiresDate`.
3. Treat `RESUBSCRIBE` as access again, not as a second first purchase, so your counts of new subscribers stay right.
4. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"SUBSCRIBED","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  if (n.notificationType !== "SUBSCRIBED") return "ignore";
  return n.subtype === "RESUBSCRIBE" ? "grant access, count a returning subscriber" : "grant access, count a new subscriber";
}

console.log(decide(notification));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `count a new subscriber` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot verifies Apple's signature, checks the bundle ID, stores the notification and answers 200. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. `SUBSCRIBED` is one of the types that update the stored purchase from the signed transaction and renewal info. A chain RevenueDot has not stored before produces `INITIAL_PURCHASE`; a chain it already holds with a new period produces `RENEWAL`, because RevenueCat reports a lapsed customer who resubscribes as a renewal and RevenueDot copies that. The subtype is not used; the stored state is.

# What does the App Store notification TEST mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/apple-test.md
Description: TEST is the notification the App Store sends when you ask for one with the Request a Test Notification endpoint. Use it to check your server receives and answers notifications.

The App Store notification TEST is a sample notification that Apple sends only when you request it, to check that your server receives notifications.

## Quick facts

| | |
|---|---|
| Notification | `notificationType` `TEST` |
| Where | App Store Server Notifications v2 (`responseBodyV2DecodedPayload`) |
| Sent by | The App Store server, to your notification URL |
| What Apple says | The App Store server sends it when you call the Request a Test Notification endpoint. You get it only at your request. |

## What triggers it

- You called Request a Test Notification in the App Store Server API,.
- It carries no purchase, so there is nothing to apply.
- Apple's Get Test Notification Status endpoint shows whether the delivery worked.

## What your server should do

1. Verify the `signedPayload` with Apple's App Store Server Library (`SignedDataVerifier.verifyAndDecodeNotification`) before you act on anything in it.
2. Answer 200 so Apple records success.
3. Do not treat it as a customer event.
4. If it does not arrive, call Get Test Notification Status for the failure reason.
5. Answer HTTP 200 (any code from 200 to 206) once you have stored the notification. Apple retries other answers five times, at 1, 12, 24, 48 and 72 hours after the previous attempt, so make your handler safe to run twice (the payload carries a `notificationUUID`).

## Example

```javascript
// Run on the decoded payload, after you verified Apple's signature.
const notification = {"notificationType":"TEST","data":{"environment":"Sandbox","bundleId":"com.example.app"}};

function decide(n) {
  if (n.notificationType !== "TEST") return "ignore";
  return "answer 200, do not touch any customer";
}

console.log(decide(notification));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `answer 200` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot verifies Apple's signature, checks the bundle ID, stores the notification and answers 200. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. RevenueDot stores the test notification, answers 200 and counts it as received, so the app's notification status in setup health can turn ready. It applies nothing and sends no webhook event.

# What does the Google Play notification ONE_TIME_PRODUCT_CANCELED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-one-time-product-canceled.md
Description: ONE_TIME_PRODUCT_CANCELED (2) means a pending one-time purchase was cancelled by the customer. Nothing was delivered, so drop any pending record.

The Google Play notification ONE_TIME_PRODUCT_CANCELED means a customer cancelled a one-time purchase that was still pending.

## Quick facts

| | |
|---|---|
| Notification | `oneTimeProductNotification.notificationType` 2, `ONE_TIME_PRODUCT_CANCELED` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |
| Sent by | Google Play, as a Cloud Pub/Sub push to your endpoint |
| What Google says | A pending one-time product purchase has been canceled by the user. |

## What triggers it

- The customer started a purchase with a delayed payment method and cancelled before it finished.
- It is about a pending purchase only. A refund of a completed purchase arrives as a voided purchase notification.
- Like the purchase type, it is sent only when you enabled one-time product events.

## What your server should do

1. Do not trust the message for the state. Google says a notification only tells you the purchase state changed; call the Google Play Developer API (`purchases.subscriptionsv2.get`) with the purchase token to get the full state.
2. Drop any pending record for that token and `sku`.
3. Do not deliver the item.
4. Do not confuse it with a refund: use the voided purchase notification for those.
5. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

## Example

```javascript
// A Pub/Sub push body: the notification is base64 JSON in message.data.
const body = { message: { messageId: "136969346945", data: Buffer.from(JSON.stringify({"version":"1.0","packageName":"com.example.app","eventTimeMillis":"1790800914000","oneTimeProductNotification":{"version":"1.0","notificationType":2,"purchaseToken":"PURCHASE_TOKEN","sku":"coins_100"}})).toString("base64") } };

function decide(body) {
  const n = JSON.parse(Buffer.from(body.message.data, "base64").toString("utf8"));
  if (!(n.oneTimeProductNotification?.notificationType === 2)) return "ignore";
  return "drop the pending purchase, deliver nothing";
}

console.log(decide(body));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `deliver nothing` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot answers every handled message with 2xx and every temporary failure with 5xx so Pub/Sub redelivers it. For subscription types it re-reads the subscription from Google with `purchases.subscriptionsv2.get` and applies that state, and it acknowledges a new purchase if the app has not. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. RevenueDot ignores it: the message is stored and answered 2xx with status `ignored`, and only type 1 (purchased) is applied. Refunds come through the voided purchase notification.

# What does the Google Play notification ONE_TIME_PRODUCT_PURCHASED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-one-time-product-purchased.md
Description: ONE_TIME_PRODUCT_PURCHASED (1) means a one-time product was bought. Fetch the purchase, deliver the item once and acknowledge or consume it.

The Google Play notification ONE_TIME_PRODUCT_PURCHASED means a customer bought a one-time product.

## Quick facts

| | |
|---|---|
| Notification | `oneTimeProductNotification.notificationType` 1, `ONE_TIME_PRODUCT_PURCHASED` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |
| Sent by | Google Play, as a Cloud Pub/Sub push to your endpoint |
| What Google says | A one-time product was successfully purchased by a user. |

## What triggers it

- A customer completed the purchase of an in-app product.
- Google sends it only if you chose to receive one-time product purchase events when you set up notifications.
- The message carries the `sku` and the `purchaseToken`.

## What your server should do

1. Do not trust the message for the state. Google says a notification only tells you the purchase state changed; call the Google Play Developer API (`purchases.subscriptionsv2.get`) with the purchase token to get the full state.
2. Call the products API with the `sku` and token, check the purchase state, and deliver the item once.
3. Acknowledge or consume the purchase so Google does not refund it.
4. Key delivery on the order so a repeat message does not give the item twice.
5. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

## Example

```javascript
// A Pub/Sub push body: the notification is base64 JSON in message.data.
const body = { message: { messageId: "136969346945", data: Buffer.from(JSON.stringify({"version":"1.0","packageName":"com.example.app","eventTimeMillis":"1790800914000","oneTimeProductNotification":{"version":"1.0","notificationType":1,"purchaseToken":"PURCHASE_TOKEN","sku":"coins_100"}})).toString("base64") } };

function decide(body) {
  const n = JSON.parse(Buffer.from(body.message.data, "base64").toString("utf8"));
  if (!(n.oneTimeProductNotification?.notificationType === 1)) return "ignore";
  return "verify, deliver once, acknowledge";
}

console.log(decide(body));
```

## How RevenueDot handles it

RevenueDot answers every handled message with 2xx and every temporary failure with 5xx so Pub/Sub redelivers it. For subscription types it re-reads the subscription from Google with `purchases.subscriptionsv2.get` and applies that state, and it acknowledges a new purchase if the app has not. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. RevenueDot fetches the product purchase for the `sku` and token, skips a purchase that is still pending, stores it under its order ID and acknowledges it. A new purchase gives `NON_RENEWING_PURCHASE`. The consumable flag comes from the product's type in your catalog.

# What does the Google Play notification SUBSCRIPTION_CANCELED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-subscription-canceled.md
Description: SUBSCRIPTION_CANCELED (3) means a subscription was cancelled by the customer, you or the system. Access continues to the expiry time; do not remove it early.

The Google Play notification SUBSCRIPTION_CANCELED means a subscription was cancelled, but the customer keeps access until the paid period ends.

## Quick facts

| | |
|---|---|
| Notification | `subscriptionNotification.notificationType` 3, `SUBSCRIPTION_CANCELED` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |
| Sent by | Google Play, as a Cloud Pub/Sub push to your endpoint |
| What Google says | A subscription was cancelled, voluntarily or involuntarily. For a voluntary cancellation, it is sent when the user cancels. |

## What triggers it

- The customer cancelled in the Play subscriptions center, you cancelled with `purchases.subscriptionsv2.cancel`, or the subscription was cancelled after account hold ran out.
- The subscription resource then has `subscriptionState` `SUBSCRIPTION_STATE_CANCELED`, and `expiryTime` says when access ends. If that time is already past, for example after a cancel during account hold, access ends now.
- `canceledStateContext` says who cancelled and `userInitiatedCancellation` can say why.

## What your server should do

1. Do not trust the message for the state. Google says a notification only tells you the purchase state changed; call the Google Play Developer API (`purchases.subscriptionsv2.get`) with the purchase token to get the full state.
2. Keep access until `expiryTime`. Google warns that removing access a customer is still entitled to violates its subscriptions policy.
3. Show a message with the end date and a way to resubscribe.
4. Read `canceledStateContext` to choose your win-back message.
5. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

## Example

```javascript
// A Pub/Sub push body: the notification is base64 JSON in message.data.
const body = { message: { messageId: "136969346945", data: Buffer.from(JSON.stringify({"version":"1.0","packageName":"com.example.app","eventTimeMillis":"1790800914000","subscriptionNotification":{"version":"1.0","notificationType":3,"purchaseToken":"PURCHASE_TOKEN"}})).toString("base64") } };

function decide(body) {
  const n = JSON.parse(Buffer.from(body.message.data, "base64").toString("utf8"));
  if (!(n.subscriptionNotification?.notificationType === 3)) return "ignore";
  return "keep access until expiryTime, show the end date";
}

console.log(decide(body));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `keep access until expiryTime` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot answers every handled message with 2xx and every temporary failure with 5xx so Pub/Sub redelivers it. For subscription types it re-reads the subscription from Google with `purchases.subscriptionsv2.get` and applies that state, and it acknowledges a new purchase if the app has not. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. RevenueDot stores the purchase as unsubscribed and sends `CANCELLATION`. The `cancel_reason` is `DEVELOPER_INITIATED` when Google says you cancelled it, `BILLING_ERROR` or `PRICE_INCREASE` when the system did, and `UNSUBSCRIBE` otherwise. A cancellation caused by an upgrade or downgrade is not a customer cancellation and is skipped. The `EXPIRATION` event comes later.

# What does the Google Play notification SUBSCRIPTION_DEFERRED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-subscription-deferred.md
Description: SUBSCRIPTION_DEFERRED (9) means a subscription's billing date was pushed later with the defer API. The customer keeps full access and is not charged during the deferral.

The Google Play notification SUBSCRIPTION_DEFERRED means the billing date of a subscription was moved later, so the customer gets more time without a charge.

## Quick facts

| | |
|---|---|
| Notification | `subscriptionNotification.notificationType` 9, `SUBSCRIPTION_DEFERRED` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |
| Sent by | Google Play, as a Cloud Pub/Sub push to your endpoint |
| What Google says | A subscription's recurrence time has been extended. |

## What triggers it

- Your backend called `purchases.subscriptionsv2.defer`, for example for a free week as a promotion or a goodwill gesture.
- During the deferral the customer has full access and is not charged. The renewal date is updated.
- For prepaid plans the defer API moves the expiration time.

1. Do not trust the message for the state. Google says a notification only tells you the purchase state changed; call the Google Play Developer API (`purchases.subscriptionsv2.get`) with the purchase token to get the full state.
2. Store the new `expiryTime` and extend access to it.
3. Record why the deferral was given, so support can explain it.
4. Do not treat it as a payment.
5. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

# What does the Google Play notification SUBSCRIPTION_EXPIRED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-subscription-expired.md
Description: SUBSCRIPTION_EXPIRED (13) means a subscription has expired. Confirm the state is expired, then remove the entitlement.

The Google Play notification SUBSCRIPTION_EXPIRED means a subscription has run out and the customer should lose access.

## Quick facts

| | |
|---|---|
| Notification | `subscriptionNotification.notificationType` 13, `SUBSCRIPTION_EXPIRED` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |

3. Mark the purchase as no longer valid in your backend.
4. Keep the customer's data, since they can resubscribe, which is a new purchase.
5. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

# What does the Google Play notification SUBSCRIPTION_IN_GRACE_PERIOD mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-subscription-in-grace-period.md
Description: SUBSCRIPTION_IN_GRACE_PERIOD (6) means a renewal payment failed and the subscription entered its grace period. Keep access and prompt the customer to fix payment.

The Google Play notification SUBSCRIPTION_IN_GRACE_PERIOD means a renewal payment failed, but the customer keeps access during the grace period.

## Quick facts

| | |
|---|---|
| Notification | `subscriptionNotification.notificationType` 6, `SUBSCRIPTION_IN_GRACE_PERIOD` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |
| Sent by | Google Play, as a Cloud Pub/Sub push to your endpoint |
| What Google says | A subscription has entered the grace period, if the grace period is enabled. |

## What triggers it

- A renewal payment failed and the base plan has a grace period. Google enables it by default on auto-renewing base plans.
- Google waits at least one day before the notification even with a grace period of zero days, to leave time for payment retries.
- The subscription resource has state `SUBSCRIPTION_STATE_IN_GRACE_PERIOD` and `expiryTime` stays in the past until the grace period ends, but entitlement should last.

## What your server should do

1. Do not trust the message for the state. Google says a notification only tells you the purchase state changed; call the Google Play Developer API (`purchases.subscriptionsv2.get`) with the purchase token to get the full state.
2. Keep access while the grace period runs.
3. Encourage the customer to fix their payment method, with a message in your app.
4. Expect `SUBSCRIPTION_RECOVERED` or `SUBSCRIPTION_RENEWED` on success, or `SUBSCRIPTION_ON_HOLD` when the grace period ends.
5. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

## Example

```javascript
// A Pub/Sub push body: the notification is base64 JSON in message.data.
const body = { message: { messageId: "136969346945", data: Buffer.from(JSON.stringify({"version":"1.0","packageName":"com.example.app","eventTimeMillis":"1790800914000","subscriptionNotification":{"version":"1.0","notificationType":6,"purchaseToken":"PURCHASE_TOKEN"}})).toString("base64") } };

function decide(body) {
  const n = JSON.parse(Buffer.from(body.message.data, "base64").toString("utf8"));
  if (!(n.subscriptionNotification?.notificationType === 6)) return "ignore";
  return "keep access, show a fix-payment message";
}

console.log(decide(body));
```

## How RevenueDot handles it

RevenueDot answers every handled message with 2xx and every temporary failure with 5xx so Pub/Sub redelivers it. For subscription types it re-reads the subscription from Google with `purchases.subscriptionsv2.get` and applies that state, and it acknowledges a new purchase if the app has not. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. RevenueDot stores a billing issue with the grace period end set to the line item's expiry, so access continues. It sends `BILLING_ISSUE` with `grace_period_expiration_at_ms` and a `CANCELLATION` with `cancel_reason: BILLING_ERROR`. If access later ends, `EXPIRATION` follows.

# What does the Google Play notification SUBSCRIPTION_PURCHASED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-subscription-purchased.md
Description: SUBSCRIPTION_PURCHASED (4) means a new subscription was purchased. Fetch its state, grant access and acknowledge it within three days or Google refunds it.

The Google Play notification SUBSCRIPTION_PURCHASED means a new subscription was purchased and has a new purchase token.

## Quick facts

| | |
|---|---|
| Notification | `subscriptionNotification.notificationType` 4, `SUBSCRIPTION_PURCHASED` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |
| Sent by | Google Play, as a Cloud Pub/Sub push to your endpoint |
| What Google says | A new subscription was purchased. |

## What triggers it

- A customer bought a subscription in your app or in the Play Store.
- A resubscribe after the old subscription expired is a new purchase with a brand new purchase token and no `linkedPurchaseToken`.
- An upgrade, downgrade or signup after cancelling from your app creates a new token with `linkedPurchaseToken` pointing to the old one.

## What your server should do

1. Do not trust the message for the state. Google says a notification only tells you the purchase state changed; call the Google Play Developer API (`purchases.subscriptionsv2.get`) with the purchase token to get the full state.
2. Call `purchases.subscriptionsv2.get`, check `subscriptionState` is `SUBSCRIPTION_STATE_ACTIVE`, and grant access.
3. Acknowledge the purchase within three days. Google says an unacknowledged purchase is refunded and revoked automatically.
4. Use `linkedPurchaseToken` or `outOfAppPurchaseContext` to connect the new token to the right customer.
5. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

## Example

```javascript
// A Pub/Sub push body: the notification is base64 JSON in message.data.
const body = { message: { messageId: "136969346945", data: Buffer.from(JSON.stringify({"version":"1.0","packageName":"com.example.app","eventTimeMillis":"1790800914000","subscriptionNotification":{"version":"1.0","notificationType":4,"purchaseToken":"PURCHASE_TOKEN"}})).toString("base64") } };

function decide(body) {
  const n = JSON.parse(Buffer.from(body.message.data, "base64").toString("utf8"));
  if (!(n.subscriptionNotification?.notificationType === 4)) return "ignore";
  return "fetch the subscription, grant access, acknowledge within three days";
}

console.log(decide(body));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `acknowledge within three days` (checked 2026-10-03).*

## How RevenueDot handles it

RevenueDot answers every handled message with 2xx and every temporary failure with 5xx so Pub/Sub redelivers it. For subscription types it re-reads the subscription from Google with `purchases.subscriptionsv2.get` and applies that state, and it acknowledges a new purchase if the app has not. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. A token RevenueDot has not stored gives an `INITIAL_PURCHASE` event; a replacement token joins the customer of its `linkedPurchaseToken`, and the old chain ends with a `PRODUCT_CHANGE` event instead of a `CANCELLATION` or `EXPIRATION`. RevenueDot acknowledges the purchase itself, and if that fails it answers 5xx so Pub/Sub retries.

# What does the Google Play notification SUBSCRIPTION_RECOVERED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-subscription-recovered.md
Description: SUBSCRIPTION_RECOVERED (1) means a subscription recovered from account hold or resumed from a pause. Restore access and extend it to the new expiry time.

The Google Play notification SUBSCRIPTION_RECOVERED means a subscription came back from account hold or from a pause.

## Quick facts

| | |
|---|---|
| Notification | `subscriptionNotification.notificationType` 1, `SUBSCRIPTION_RECOVERED` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |
| Sent by | Google Play, as a Cloud Pub/Sub push to your endpoint |
| What Google says | A subscription was recovered from account hold or resumed from a pause. |

## What triggers it

- The customer fixed their payment method during account hold, and the retried payment worked. The purchase token stays the same.
- A paused subscription resumed, at the end of the pause or because the customer resumed it by hand.
- The billing date moves to the recovery date.

## What your server should do

1. Do not trust the message for the state. Google says a notification only tells you the purchase state changed; call the Google Play Developer API (`purchases.subscriptionsv2.get`) with the purchase token to get the full state.
2. Restore access and extend it to the new `expiryTime`.
3. Remove any fix-payment or paused message in your app.
4. Do not count it as a new subscriber.
5. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

```javascript
  const n = JSON.parse(Buffer.from(body.message.data, "base64").toString("utf8"));
  if (!(n.subscriptionNotification?.notificationType === 1)) return "ignore";
  return "restore access, extend to the new expiryTime";
}

```

# What does the Google Play notification SUBSCRIPTION_RENEWED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-subscription-renewed.md
Description: SUBSCRIPTION_RENEWED (2) means an active subscription renewed. Fetch the new expiry time and extend access. Renewals need no acknowledgement.

The Google Play notification SUBSCRIPTION_RENEWED means an active subscription renewed for another period.

## Quick facts

| | |
|---|---|
| Notification | `subscriptionNotification.notificationType` 2, `SUBSCRIPTION_RENEWED` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |
| Sent by | Google Play, as a Cloud Pub/Sub push to your endpoint |
| What Google says | An active subscription was renewed. |

## What triggers it

- The renewal charge succeeded on the billing date.
- For installment subscriptions, Google sends it each time a payment is charged on its billing date.
- Renewals do not need to be acknowledged.

1. Do not trust the message for the state. Google says a notification only tells you the purchase state changed; call the Google Play Developer API (`purchases.subscriptionsv2.get`) with the purchase token to get the full state.

3. Do not acknowledge a renewal: Google says it is not needed.
4. Keep the order ID (`latestOrderId`), which is new for every renewal.
5. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

# What does the Google Play notification SUBSCRIPTION_RESTARTED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-subscription-restarted.md
Description: SUBSCRIPTION_RESTARTED (7) means the customer restored a cancelled subscription from Play before it expired. It keeps its purchase token and renews again.

The Google Play notification SUBSCRIPTION_RESTARTED means a customer undid a cancellation before the subscription expired.

## Quick facts

| | |
|---|---|
| Notification | `subscriptionNotification.notificationType` 7, `SUBSCRIPTION_RESTARTED` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |
| Sent by | Google Play, as a Cloud Pub/Sub push to your endpoint |
| What Google says | The user restored their subscription from Play, Account, Subscriptions. The subscription was cancelled but had not expired when the user restored it. |

## What triggers it

- The customer tapped Resubscribe on a cancelled subscription that was still running. Google calls this a restore.
- The same purchase token continues and all cancellation fields are cleared.
- After expiry the same action is a new purchase and arrives as `SUBSCRIPTION_PURCHASED`.

1. Do not trust the message for the state. Google says a notification only tells you the purchase state changed; call the Google Play Developer API (`purchases.subscriptionsv2.get`) with the purchase token to get the full state.
2. Record that the subscription is set to renew again and stop showing restore messages.
3. Do not grant anything new: the customer already has access until `expiryTime`.
4. Stop your win-back flow for this customer.
5. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

# What does the Google Play notification VOIDED_PURCHASE mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/notifications/google-voided-purchase.md
Description: A voidedPurchaseNotification means Google voided a purchase: a refund, chargeback or revocation. Revoke the item or access using the order ID and refund type.

A Google Play voidedPurchaseNotification means a purchase was voided, usually by a refund or a chargeback, so what it granted should be taken back.

## Quick facts

| | |
|---|---|
| Notification | `voidedPurchaseNotification` |
| Where | Google Play real-time developer notifications (Pub/Sub, `DeveloperNotification`) |
| Sent by | Google Play, as a Cloud Pub/Sub push to your endpoint |
| What Google says | A purchase has been voided. The message gives the purchase token, the order ID, the product type (subscription or one-time) and the refund type (full or quantity-based partial). |

## What triggers it

- The customer was refunded, charged back, or you revoked the purchase.
- `productType` 1 is a subscription and 2 a one-time product. `refundType` 1 is a full refund and 2 a quantity-based partial refund of a multi-quantity purchase.
- For subscriptions, a new order ID is created for each renewal, so the order ID says which period was voided.

## What your server should do

1. Find the purchase by `purchaseToken` and `orderId` and revoke what that order granted.
2. For a partial refund, adjust the quantity instead of revoking everything. `refundableQuantity` in the products API gives what is left.
3. For more data, use Google's Voided Purchases API, a pull model over a time range.
4. Answer 2xx once you have handled the message, and skip a `messageId` you have seen: Google recommends checking the uniqueness of message IDs so a redelivery does not make a second API call.

## Example

```javascript
// A Pub/Sub push body: the notification is base64 JSON in message.data.
const body = { message: { messageId: "136969346945", data: Buffer.from(JSON.stringify({"version":"1.0","packageName":"com.example.app","eventTimeMillis":"1790800914000","voidedPurchaseNotification":{"purchaseToken":"PURCHASE_TOKEN","orderId":"GPA.1234-5678-9012-34567","productType":1,"refundType":1}})).toString("base64") } };

function decide(body) {
  const n = JSON.parse(Buffer.from(body.message.data, "base64").toString("utf8"));
  if (!(n.voidedPurchaseNotification)) return "ignore";
  const v = n.voidedPurchaseNotification;
  if (v.refundType === 2) return "reduce the quantity, keep the purchase";
  return v.productType === 1 ? "revoke the subscription period of this order" : "revoke the one-time item";
}

console.log(decide(body));
```

RevenueDot answers every handled message with 2xx and every temporary failure with 5xx so Pub/Sub redelivers it. For subscription types it re-reads the subscription from Google with `purchases.subscriptionsv2.get` and applies that state, and it acknowledges a new purchase if the app has not. A purchase RevenueDot has not seen is applied only when the app's **Track new purchases from server-to-server notifications** setting is on. For a subscription RevenueDot marks the voided period refunded (only if the order is the current one) and sends `CANCELLATION` with `cancel_reason: CUSTOMER_SUPPORT` and a negative price. A one-time purchase is marked refunded the same way. A partial quantity refund (`refundType` 2) of a one-time product is ignored. A daily scan of Google's voided purchases catches refunds whose message never arrived.
