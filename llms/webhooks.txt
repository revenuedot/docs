# What does the RevenueDot webhook event BILLING_ISSUE mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/webhooks/webhook-billing-issue.md
Description: BILLING_ISSUE is sent when a renewal charge fails. The store retries and access may continue in a grace period. Prompt the customer to fix their payment method.

The RevenueDot webhook event BILLING_ISSUE means a subscription's renewal payment failed and the store is retrying it.

## Quick facts

| | |
|---|---|
| Event | `BILLING_ISSUE` |
| Where | RevenueDot webhook (`event.type`), RevenueCat's webhook format |
| Sent to | Every enabled webhook whose filters match |
| Fields that are specific to it | `grace_period_expiration_at_ms` |
| What it means | A renewal charge failed. The store retries; access may continue in a grace period. |

## When it is sent

- The store could not charge the customer's payment method at renewal.
- `grace_period_expiration_at_ms` is always present and is null when there is no grace period.
- RevenueDot also sends a `CANCELLATION` with `cancel_reason: BILLING_ERROR`, as RevenueCat does.

## What your server should do

1. Keep access until `grace_period_expiration_at_ms` when it is set, otherwise follow the store's guidance for your app.
2. Ask the customer to update their payment method.
3. Expect `RENEWAL` if billing recovers, or `EXPIRATION` with `BILLING_ERROR` if the store gives up.
4. Deduplicate on `event.id`: deliveries can repeat, because anything but HTTP 200 is retried after 5, 10, 20, 40 and 80 minutes.

## Example

```javascript
import { createHmac, timingSafeEqual } from "node:crypto";

// X-RevenueCat-Webhook-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">
function verify(rawBody, header, secret, toleranceSeconds = 300) {
  const m = /^t=(\d+),v1=([0-9a-f]{64})$/.exec(header ?? "");
  if (!m || Math.abs(Date.now() / 1000 - Number(m[1])) > toleranceSeconds) return false;
  const expected = createHmac("sha256", secret).update(`${m[1]}.${rawBody}`).digest();
  return timingSafeEqual(expected, Buffer.from(m[2], "hex"));
}

// Sign a sample delivery the way RevenueDot does, then handle it.
const secret = "whsec_test_secret";
const rawBody = JSON.stringify({ api_version: "1.0", event: {"id":"66339910-3BFF-49F4-B873-D1283D673DE2","type":"BILLING_ISSUE","app_user_id":"user_1","product_id":"pro_monthly","grace_period_expiration_at_ms":1790900000000} });
const t = Math.floor(Date.now() / 1000);
const header = `t=${t},v1=${createHmac("sha256", secret).update(`${t}.${rawBody}`).digest("hex")}`;

const seen = new Set(); // use a database table in production

function handle(rawBody, header) {
  if (!verify(rawBody, header, secret)) return "401 bad signature";
  const { event } = JSON.parse(rawBody);
  if (seen.has(event.id)) return "200 duplicate";
  seen.add(event.id);
  if (event.type !== "BILLING_ISSUE") return "200 ignored";
  const grace = event.grace_period_expiration_at_ms;
  return grace ? "keep access until " + new Date(grace).toISOString().slice(0, 10) + ", ask to fix payment" : "ask to fix payment";
}

console.log(handle(rawBody, header));
```

## How RevenueDot produces it

`diffSubscription` returns `BILLING_ISSUE` when a billing issue time appears on the stored purchase. Apple's `DID_FAIL_TO_RENEW` and Google's `SUBSCRIPTION_IN_GRACE_PERIOD` and `SUBSCRIPTION_ON_HOLD` all set it.

# What does the RevenueDot webhook event CANCELLATION mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/webhooks/webhook-cancellation.md
Description: CANCELLATION is sent when auto-renew is turned off or a purchase is refunded. Access continues to the expiry time unless it was a refund. Check cancel_reason.

The RevenueDot webhook event CANCELLATION means a subscription will not renew, or a purchase was refunded.

## Quick facts

| | |
|---|---|
| Event | `CANCELLATION` |
| Where | RevenueDot webhook (`event.type`), RevenueCat's webhook format |
| Sent to | Every enabled webhook whose filters match |
| Fields that are specific to it | `cancel_reason` |
| What it means | Auto-renew was turned off, or the purchase was refunded. Access continues to `expiration_at_ms` unless it was a refund. A refund has `cancel_reason: CUSTOMER_SUPPORT` and a negative price. |

## When it is sent

- The customer turned auto-renew off (`cancel_reason: UNSUBSCRIBE`), the store gave a reason such as `DEVELOPER_INITIATED` or `PRICE_INCREASE`, or a billing failure counted as a cancellation (`BILLING_ERROR`).
- A refund gives `cancel_reason: CUSTOMER_SUPPORT` and a negative `price`.
- It is not the end of access. `EXPIRATION` follows when the paid period ends.

## What your server should do

1. For an unsubscribe, keep access until `expiration_at_ms` and start your win-back flow.
2. For `CUSTOMER_SUPPORT` with a negative price, revoke access now.
3. Use `cancel_reason` to separate voluntary from billing-related churn.
4. Deduplicate on `event.id`: deliveries can repeat, because anything but HTTP 200 is retried after 5, 10, 20, 40 and 80 minutes.

## Example

```javascript

  const expected = createHmac("sha256", secret).update(`${m[1]}.${rawBody}`).digest();
  return timingSafeEqual(expected, Buffer.from(m[2], "hex"));
}

const rawBody = JSON.stringify({ api_version: "1.0", event: {"id":"66339910-3BFF-49F4-B873-D1283D673DE2","type":"CANCELLATION","app_user_id":"user_1","product_id":"pro_monthly","cancel_reason":"UNSUBSCRIBE"} });
const t = Math.floor(Date.now() / 1000);
const header = `t=${t},v1=${createHmac("sha256", secret).update(`${t}.${rawBody}`).digest("hex")}`;

  seen.add(event.id);
  if (event.type !== "CANCELLATION") return "200 ignored";
  if (event.cancel_reason === "CUSTOMER_SUPPORT") return "revoke access now, book the refund";

}

console.log(handle(rawBody, header));
```

## How RevenueDot produces it

`diffSubscription` returns `CANCELLATION` when auto-renew goes off (with the reason from the store, or `BILLING_ERROR` when a billing issue is stored, else `UNSUBSCRIBE`) and, with `isRefund`, when a refund time appears (reason `CUSTOMER_SUPPORT`). One-time purchases get the refund form too.

# What does the RevenueDot webhook event EXPERIMENT_ENROLLMENT mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/webhooks/webhook-experiment-enrollment.md
Description: EXPERIMENT_ENROLLMENT is sent once per customer and experiment when a customer joins an offering experiment. It carries no app, so app-scoped webhooks do not get it.

The RevenueDot webhook event EXPERIMENT_ENROLLMENT means a customer joined an offering experiment.

## Quick facts

| | |
|---|---|
| Event | `EXPERIMENT_ENROLLMENT` |
| Where | RevenueDot webhook (`event.type`), RevenueCat's webhook format |
| Sent to | Every enabled webhook whose filters match |
| Fields that are specific to it | `experiment_id`, `experiment_variant`, `offering_id`, `experiment_enrolled_at_ms` |
| What it means | A customer joined an offering experiment: the first offerings request that enrolled them. Sent once per customer and experiment, as a production event with no app. |

## When it is sent

- The first offerings request of a customer that matches an experiment's targeting enrolls them in a variant.
- It is sent once per customer and experiment.
- It is a production event with no app, so a webhook set to sandbox only, or to one app, does not get it.

## What your server should do

1. Store the `experiment_id` and `experiment_variant` (`a` is the control) against the customer so your analytics can split results.
2. Do not use it to grant anything.
3. Use a webhook set to production and all apps if you need it.
4. Deduplicate on `event.id`: deliveries can repeat, because anything but HTTP 200 is retried after 5, 10, 20, 40 and 80 minutes.

## Example

# What does the RevenueDot webhook event EXPIRATION mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/webhooks/webhook-expiration.md
Description: EXPIRATION is sent when access ended: the period ran out, billing retry gave up, or the subscription paused. Remove access and read expiration_reason.

The RevenueDot webhook event EXPIRATION means a customer's access has ended.

## Quick facts

| | |
|---|---|
| Event | `EXPIRATION` |
| Where | RevenueDot webhook (`event.type`), RevenueCat's webhook format |
| Sent to | Every enabled webhook whose filters match |
| Fields that are specific to it | `expiration_reason` |
| What it means | Access ended: the period ran out, billing retry gave up or the subscription paused. |

## When it is sent

- The paid period, and any grace period, passed with no renewal.
- `expiration_reason` says why: `UNSUBSCRIBE`, `BILLING_ERROR`, `DEVELOPER_INITIATED`, `PRICE_INCREASE`, `CUSTOMER_SUPPORT`, `UNKNOWN` or `SUBSCRIPTION_PAUSED`.
- It is recorded once per period by a scheduled job that runs every minute, so it can arrive up to a minute after the expiry time.

## What your server should do

1. Remove the entitlements of the subscription.
2. Use `expiration_reason` to choose the win-back message: a billing error needs a payment prompt.
3. Keep the customer's data.
4. Deduplicate on `event.id`: deliveries can repeat, because anything but HTTP 200 is retried after 5, 10, 20, 40 and 80 minutes.

## Example

```javascript
import { createHmac, timingSafeEqual } from "node:crypto";

// X-RevenueCat-Webhook-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">

}

// Sign a sample delivery the way RevenueDot does, then handle it.
const secret = "whsec_test_secret";
const rawBody = JSON.stringify({ api_version: "1.0", event: {"id":"66339910-3BFF-49F4-B873-D1283D673DE2","type":"EXPIRATION","app_user_id":"user_1","product_id":"pro_monthly","expiration_reason":"BILLING_ERROR"} });
const t = Math.floor(Date.now() / 1000);
const header = `t=${t},v1=${createHmac("sha256", secret).update(`${t}.${rawBody}`).digest("hex")}`;

const seen = new Set(); // use a database table in production

function handle(rawBody, header) {
  if (!verify(rawBody, header, secret)) return "401 bad signature";
  const { event } = JSON.parse(rawBody);
  if (seen.has(event.id)) return "200 duplicate";
  seen.add(event.id);
  if (event.type !== "EXPIRATION") return "200 ignored";
  return event.expiration_reason === "BILLING_ERROR" ? "remove access, ask for a new payment method" : "remove access, start win-back";
}

console.log(handle(rawBody, header));
```

*Run-checked: `npm run check:snippets` runs this snippet with Node and compares its output with `ask for a new payment method` (checked 2026-10-03).*

## How RevenueDot produces it

A scheduled job (`services/tick.ts`) records `EXPIRATION` for every subscription whose access, grace period included, has ended, and claims each one once so replicas do not send it twice. The reason comes from the stored state: paused, then a billing issue, then the stored cancel reason, else `UNSUBSCRIBE`.

# What does the RevenueDot webhook event INITIAL_PURCHASE mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/webhooks/webhook-initial-purchase.md
Description: INITIAL_PURCHASE is sent when a customer first buys a subscription, including a free trial start. Grant access to the entitlements and record the customer.

The RevenueDot webhook event INITIAL_PURCHASE means a customer bought a subscription for the first time, including the start of a free trial.

## Quick facts

| | |
|---|---|
| Event | `INITIAL_PURCHASE` |
| Where | RevenueDot webhook (`event.type`), RevenueCat's webhook format |
| Sent to | Every enabled webhook whose filters match |
| Fields that are specific to it | none beyond the common subscription fields |
| What it means | The first purchase of a subscription, including a free trial start. |

## When it is sent

- A subscription chain that RevenueDot has not seen before is recorded, from the SDK, a store notification (when new purchases are tracked), an import or a web checkout.
- `period_type` is `TRIAL` for a free trial and `INTRO` for a paid introductory offer; `NORMAL` otherwise.
- It is sent once per chain. A lapsed customer who comes back gets `RENEWAL`, not a second `INITIAL_PURCHASE`.

## What your server should do

1. Grant the entitlements in `entitlement_ids` until `expiration_at_ms`.
2. Record `original_transaction_id` as the key for the whole subscription.
3. In a trial, do not count revenue yet: `price` is the money that moved, and is 0 for a free trial.
4. Deduplicate on `event.id`: deliveries can repeat, because anything but HTTP 200 is retried after 5, 10, 20, 40 and 80 minutes.

## Example

# What does the RevenueDot webhook event PRODUCT_CHANGE mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/webhooks/webhook-product-change.md
Description: PRODUCT_CHANGE is sent when a customer changes product: an upgrade now, or a downgrade or crossgrade scheduled for the next renewal. product_id is the old product.

The RevenueDot webhook event PRODUCT_CHANGE means a customer switched a subscription to another product, now or at the next renewal.

## Quick facts

| | |
|---|---|
| Event | `PRODUCT_CHANGE` |
| Where | RevenueDot webhook (`event.type`), RevenueCat's webhook format |
| Sent to | Every enabled webhook whose filters match |
| Fields that are specific to it | `new_product_id` |
| What it means | The customer changed product: an upgrade now, or a downgrade or crossgrade scheduled for the next renewal. `product_id` is the old product. |

## When it is sent

- An upgrade takes effect at once. The event names the old product in `product_id` and the new one in `new_product_id`.
- A downgrade or crossgrade is announced when it is scheduled, and takes effect at the next renewal.
- A scheduled switch reaching its renewal is only a `RENEWAL`, because it was announced before.

## What your server should do

1. For an upgrade, switch the entitlement to `new_product_id` now.
2. For a scheduled change, keep the current product and plan the switch for the renewal.
3. Do not treat the old product's end as a cancellation: no `CANCELLATION` or `EXPIRATION` is sent for it.
4. Deduplicate on `event.id`: deliveries can repeat, because anything but HTTP 200 is retried after 5, 10, 20, 40 and 80 minutes.

## Example

```javascript
import { createHmac, timingSafeEqual } from "node:crypto";

  const expected = createHmac("sha256", secret).update(`${m[1]}.${rawBody}`).digest();
  return timingSafeEqual(expected, Buffer.from(m[2], "hex"));
}

// Sign a sample delivery the way RevenueDot does, then handle it.
const secret = "whsec_test_secret";
const rawBody = JSON.stringify({ api_version: "1.0", event: {"id":"66339910-3BFF-49F4-B873-D1283D673DE2","type":"PRODUCT_CHANGE","app_user_id":"user_1","product_id":"pro_monthly","new_product_id":"pro_annual"} });
const t = Math.floor(Date.now() / 1000);
const header = `t=${t},v1=${createHmac("sha256", secret).update(`${t}.${rawBody}`).digest("hex")}`;

const seen = new Set(); // use a database table in production

  if (!verify(rawBody, header, secret)) return "401 bad signature";
  const { event } = JSON.parse(rawBody);
  if (seen.has(event.id)) return "200 duplicate";
  seen.add(event.id);
  if (event.type !== "PRODUCT_CHANGE") return "200 ignored";
  return "move " + event.app_user_id + " from " + event.product_id + " to " + event.new_product_id;
}
```

# What does the RevenueDot webhook event SUBSCRIPTION_EXTENDED mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/webhooks/webhook-subscription-extended.md
Description: SUBSCRIPTION_EXTENDED is sent when a period got longer without a new payment: an App Store renewal extension or a Google Play deferral. Extend access to the new date.

The RevenueDot webhook event SUBSCRIPTION_EXTENDED means a subscription's current period was made longer without a payment.

## Quick facts

| | |
|---|---|
| Event | `SUBSCRIPTION_EXTENDED` |
| Where | RevenueDot webhook (`event.type`), RevenueCat's webhook format |
| Sent to | Every enabled webhook whose filters match |
| What it means | The current period got longer without a new payment: an App Store renewal extension or a Google Play deferral. |

## When it is sent

- On the App Store, your server extended the renewal date (`RENEWAL_EXTENDED`).
- On Google Play, your server deferred billing (`SUBSCRIPTION_DEFERRED`).
- The period start does not change, only `expiration_at_ms` moves later. `price` is 0.

## What your server should do

1. Extend access to the new `expiration_at_ms`.
2. Do not count revenue: no money moved.
3. Record why the extension was given.
4. Deduplicate on `event.id`: deliveries can repeat, because anything but HTTP 200 is retried after 5, 10, 20, 40 and 80 minutes.

## Example


# What does the RevenueDot webhook event UNCANCELLATION mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/webhooks/webhook-uncancellation.md
Description: UNCANCELLATION is sent when a customer turns auto-renew back on before the subscription expires. Stop the win-back flow; access never stopped.

The RevenueDot webhook event UNCANCELLATION means a customer turned auto-renew back on before their subscription ended.

## Quick facts

| | |
|---|---|
| Event | `UNCANCELLATION` |
| Where | RevenueDot webhook (`event.type`), RevenueCat's webhook format |
| Sent to | Every enabled webhook whose filters match |
| What it means | Auto-renew was turned back on before the subscription expired. |

## When it is sent

- The customer resubscribed in the store settings after cancelling, while the paid period was still running.
- On Google Play this is a restore (`SUBSCRIPTION_RESTARTED`); on the App Store it is `DID_CHANGE_RENEWAL_STATUS` with `AUTO_RENEW_ENABLED`.
- Recovering a failed payment is a `RENEWAL`, not this event.

## What your server should do

1. Stop any win-back message or offer for this customer.
2. Mark the subscription as renewing again.
3. Do not change access: it never stopped.
4. Deduplicate on `event.id`: deliveries can repeat, because anything but HTTP 200 is retried after 5, 10, 20, 40 and 80 minutes.

## Example

```javascript
import { createHmac, timingSafeEqual } from "node:crypto";

// X-RevenueCat-Webhook-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">
function verify(rawBody, header, secret, toleranceSeconds = 300) {
  const m = /^t=(\d+),v1=([0-9a-f]{64})$/.exec(header ?? "");
  if (!m || Math.abs(Date.now() / 1000 - Number(m[1])) > toleranceSeconds) return false;
  const expected = createHmac("sha256", secret).update(`${m[1]}.${rawBody}`).digest();
  return timingSafeEqual(expected, Buffer.from(m[2], "hex"));
}

// Sign a sample delivery the way RevenueDot does, then handle it.
const secret = "whsec_test_secret";
const rawBody = JSON.stringify({ api_version: "1.0", event: {"id":"66339910-3BFF-49F4-B873-D1283D673DE2","type":"UNCANCELLATION","app_user_id":"user_1","product_id":"pro_monthly"} });
const t = Math.floor(Date.now() / 1000);
const header = `t=${t},v1=${createHmac("sha256", secret).update(`${t}.${rawBody}`).digest("hex")}`;

const seen = new Set(); // use a database table in production

function handle(rawBody, header) {
  if (!verify(rawBody, header, secret)) return "401 bad signature";
  const { event } = JSON.parse(rawBody);
  if (seen.has(event.id)) return "200 duplicate";
  seen.add(event.id);
  if (event.type !== "UNCANCELLATION") return "200 ignored";
  return "stop win-back, mark " + event.app_user_id + " as renewing";
}

console.log(handle(rawBody, header));
```

## How RevenueDot produces it

`diffSubscription` returns `UNCANCELLATION` when the stored purchase was unsubscribed and the new state is not, unless the change is a renewal that recovered a billing issue.

# What does the RevenueDot webhook event VIRTUAL_CURRENCY_TRANSACTION mean?

Source: https://raw.githubusercontent.com/revenuedot/docs/main/docs/webhooks/webhook-virtual-currency-transaction.md
Description: VIRTUAL_CURRENCY_TRANSACTION is sent when an in-app currency was credited because a purchase was recorded or a rewarded ad was verified. Credit it in your game once.

The RevenueDot webhook event VIRTUAL_CURRENCY_TRANSACTION means a customer was credited with an in-app currency.

## Quick facts

| | |
|---|---|
| Event | `VIRTUAL_CURRENCY_TRANSACTION` |
| Where | RevenueDot webhook (`event.type`), RevenueCat's webhook format |
| Sent to | Every enabled webhook whose filters match |
| Fields that are specific to it | `source` |
| What it means | An in-app currency was credited because a purchase of a granting product was recorded (`source: in_app_purchase`), or because a rewarded ad was verified and a reward rule granted currency (`source: ad_reward`, a RevenueDot extension). Not sent for adjustments made through the API. |

## When it is sent

- A purchase of a product that grants currency was recorded (`source: in_app_purchase`).
- A rewarded ad was verified and a reward rule granted currency (`source: ad_reward`). For that source, `product_id` and `store` are null.
- Adjustments you make through the API do not send it.

## What your server should do

1. Credit the currency once, keyed on `event.id` or the transaction ID.
2. Branch on `source` if you treat ad rewards differently from purchases.
3. Do not treat it as revenue: the purchase has its own event.
4. Deduplicate on `event.id`: deliveries can repeat, because anything but HTTP 200 is retried after 5, 10, 20, 40 and 80 minutes.
